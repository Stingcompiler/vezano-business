# Sting Systems — وثيقة تصميم النظام

**التاريخ:** 2026-09-15 · **الحالة:** مشتقّة من الوثيقة v21 — لا قرار جديد فيها؛ كل بند يحمل مرجعه (§) وأي انحراف مستقبلي يمرّ بـ`docs/decisions/`
**الغرض:** خريطة معمارية واحدة للمنفّذين والمراجعين: المكوّنات، تدفق البيانات، العقود، التخزين، المفاضلات، وما يُعاد النظر فيه مع النمو. التفصيل التنفيذي في `docs/PLAN.md`، والإصدارات في `docs/decisions/0001`.

## ١ · المتطلبات

### الوظيفية (§١.٣)
- نقطة بيع تعمل بلا اتصال: بيع نقدي/آجل/مختلط، باركود، وحدة ووزن، خصم منسوب.
- دفتر أطراف: عملاء وموردون، سداد، كشف حساب، أرصدة افتتاحية، دمج مضبوط.
- مخزون: استلام، جرد أعمى، هالك، تحويلات بين فروع.
- ورديات وعدّ صندوق؛ طباعة عربية حرارية؛ استيراد بمعاينة؛ تصدير واستعادة.
- إشعارات (منصة/محل/زبون) وبوابة زبون PWA خفيفة.
- سوق توريد B2B (M1 اكتشاف ونشر، M2 تفاوض وتنفيذ) ضمن الإصدار الأول للويب (§١٥.٥).

### غير الوظيفية (§١٨.٣، §١٣.٤)
| المقياس | الهدف الأولي (يُقاس ولا يُوعد به) |
|---|---|
| بحث محلي | p95 < 300ms |
| حفظ بيع محلي (دون طباعة) | p95 < 1s |
| إيصال على طراز معتمد | < 10s |
| RPO خادمي | ≤ 15 دقيقة |
| RTO | ≤ 4 ساعات |
| فقد بسبب المزامنة | صفر — معيار قبول مطلوب (§٨.١٢) |

### القيود (§١.١، §١٥.٣)
- فريق: صاحب المشروع يعتمد، وClaude/Codex ينفّذان ويتراجعان — لذلك Modular Monolith لا خدمات مصغرة.
- السوق: السودان؛ شبكة متقطعة وعتاد متواضع → **البيانات المحلية هي مصدر حقيقة العمليات غير المؤكدة** (§٤.١).
- عربية وRTL أولاً؛ عملة واحدة لكل مستأجر مثبتة (§٦.٣).
- ترتيب المنصات ملزم: ويب/PWA → Expo → Tauri (§١٥.١).

## ٢ · التصميم العالي

### مخطط المكوّنات (§٤.١، §٤.٤)

```
                          ┌──────────────────────────────────────────┐
                          │  backend/ — Django 5 · DRF (Monolith)    │
  apps/web (Next.js 15)   │  ┌────────┬────────┬─────────┬────────┐  │
  POS·إدارة·بوابة·سوق ───▶│  │ core   │ sync   │ parties │ catalog│  │
        │ PWA/SW          │  ├────────┼────────┼─────────┼────────┤  │
  apps/mobile (Expo) ────▶│  │inventory│ sales │purchasing│notif. │  │
        │ SQLite          │  ├────────┴───┬────┴─────────┴────────┤  │
  apps/desktop (Tauri) ──▶│  │marketplace │ verticals (مؤجل)      │  │
        │ SQLite          │  └────────────┴───────────────────────┘  │
        │                 │        │ outbox │ ORM+RLS               │
        │                 └────────┼────────┼───────────────────────┘
        │                          ▼        ▼
        │                  Celery·Redis   PostgreSQL 16 (RLS)
        │                  (جدولة/إشعارات   + نسخ دورية وPITR
        │                   فقط — لا صحة بيع)  على تخزين مستقل (§١٣.٤)
        │
  الحزم المشتركة (§٤.٦): contracts ← OpenAPI │ domain (مال/كميات/آثار)
  sync-core (بروتوكول ٨) │ platform (تخزين/أسرار/طباعة كمنافذ)
  ui-web (٢٩ مكوناً) │ design (رموز DS-1.2 + الحالات الـ١٧)
```

- **اتجاه الاعتماد:** `apps/*` → نواة TS (`domain`+`sync-core`) → عقود `platform`؛ النواة لا تستورد React/DOM/Dexie/SQLite (§٤.٦ بند ١) — يفرضه dependency-cruiser في CI.
- **الخادم مرجع القبول**، وقاعدة الجهاز مرجع ما حُفظ ولم يُؤكَّد (§٤.١). لا CRDT: ثبات الأحداث + تحقق خادمي (§٨.١).

### تدفق البيانات — بيع أثناء انقطاع (§٣.٢، §٨.٢–٨.٣، §٨.٨)

```
كاشير ─▶ POS (CSR من الإسقاط المحلي)
  │ تحقق محلي (domain): حساب، صلاحية، سعة
  ▼
معاملة محلية واحدة (Dexie/SQLite):
  Operation(sale) + Sale + SaleLine + Payment + StockMovement
  + تحديث الإسقاطات + created_local_seq + وصف الرفع        ← «نجاح» هنا
  ▼                                                    (الطباعة لاحقة؛
طابور sync-core: local → pending                        فشلها لا يلغي)
  │ عند الاتصال: PUSH بهويات UUIDv7 الأصلية
  ▼
الخادم: قفل المستأجر → معاملة مستقلة لكل عملية → تحقق واشتقاق
  → COMMIT → server_seq من عداد المستأجر → ACK بإيصالات الأعضاء
  ▼
الجهاز: انتقال ذرّي ③→②/① وفق معادلة الرصيد:
  balance = snapshot(S) + Σمؤكد(seq>S) + Σغير مؤكد خارج اللقطة
انقطاع الرد؟ إعادة بنفس الهويات → duplicate للملتزم، لا أثر مكرر
```

### عقود API (§٨.٣–٨.٧، §٩.٤)
- **PUSH** `/sync/push`: غلاف `{protocol_version, sync_epoch, request_id, operations[]}`؛ كل عملية `{operation_id, kind, op_version, dependencies, members[]}`؛ النتائج `accepted | duplicate | conflicted | rejected` مع `member_receipts` و`server_seq_high` (تشخيصي — لا تُقدَّم مؤشرات إليه).
- **PULL** `/sync/pull`: صفحة من معاملة `REPEATABLE READ` واحدة؛ مؤشر لكل `(scope, entity_group)`؛ `entities + operation_projections + tombstones + access_manifest_version + cursors + has_more + snapshot_candidates`.
- **REST** للإدارة والسوق عبر DRF، مولَّد إلى `packages/contracts` بـOpenAPI 3.1 — مصدر الأنواع الوحيد.
- **مصادقة:** JWT (وصول قصير + تجديد مدوّر + إلغاء)؛ Cookies آمنة HttpOnly للويب؛ SecureStore للموبايل؛ مخزن نظام للديسكتوب. PIN محلي لا يمرّ بالخادم (§٩.١).

### خيارات التخزين (§٨.١٣، §١٢.١)
| الموضع | التقنية | الضابط |
|---|---|---|
| مركزي | PostgreSQL 16 | RLS ثلاثي الطبقات (§٥.٤)، قيود مؤجلة داخل العملية، أرصدة كإسقاطات |
| ويب | Dexie/IndexedDB | BigInt بلا مرور بـNumber؛ كاتب منسّق بين التبويبات؛ تخزين مستديم كبوابة تجهيز (§١٣.١) |
| موبايل/ديسكتوب | SQLite (expo-sqlite / تكامل Tauri) | نفس عقد `platform`؛ اختبارات العقد تُعاد على كل محوّل فعلي |
| كاش خادمي | TanStack Query (عميل) + ISR للعام فقط | لا بيانات مستأجر في كاش عام (§١٢.٤) |

## ٣ · التعمق

### نموذج البيانات (§٥)
- الكيانات: `Tenant→Branch→Device`، `Party→PartyLedgerEntry`، `Item→ItemUnit/Barcode`، `Operation→{Sale,SaleLine,Payment,StockMovement,LedgerEntry}`، أحداث الوردية، `Snapshot/SyncCursor/AuditEvent`، وكيانات السوق (§٥.٥).
- كل حدث: `id, operation_id, tenant_id, branch_id, device_id, actor_user_id, occurred_at, business_date, received_at, sync_epoch, server_seq, content_hash, schema_version` (§٥.٣).
- **لا تعديل لحقول أعمال معتمدة**: التصحيح حركة عكسية مستقلة (§٥.٢). المال `BIGINT` بالوحدة الصغرى، الكمية بأجزاء الألف، التقريب نصف بعيداً عن الصفر في `packages/domain` وحدها (§٦).
- العزل: RLS بلا `BYPASSRLS` لدور التطبيق + `TenantContext` يفشل عند غيابه + مفاتيح مركبة `(tenant_id, …)` (§٥.٤).

### الطوابير والأحداث (§٤.٣، §١١.٧)
- **أثر صحة البيع داخل معاملة العملية — أبداً ليس في مهمة خلفية.**
- **Outbox** يُكتب في نفس المعاملة للإشعارات وإسقاطات النشر؛ المستهلك (Celery) يمنع تكرار الأثر بمفتاح idempotency لكل (مستلم، قناة، واقعة).
- Celery Beat بقائد واحد؛ هوية مستقرة لكل واقعة دورية.

### الأخطاء وإعادة المحاولة (§٨.٣)
- عابر (شبكة/429/5xx): تراجع أُسّي + jitter + حدّ أقصى، بلا إسقاط بعد عدد محاولات.
- دائم (تحقق/مخطط): حجر فوري بلا سدّ الطابور؛ رفض المصادقة → مسار تجديد/استرداد لا حلقة.
- انقطاع الرد ≠ فشل: إعادة بنفس الهويات.

## ٤ · السعة والاعتمادية

- **الحمل المفترض** (نطاق الإثبات §١.٢ والتوسع ز §١٥.١): 5–10 عملاء أوائل، جهازان لكل فرع، مئات العمليات يومياً للجهاز — كل رقم سعة يُقاس قبل أن يُعلن (§١٨.٣: التقرير يسجل العتاد والأحجام).
- **نقطة التسلسل المعروفة:** قفل عداد المستأجر يسرلسل كتابته (§٨.٥) — مقبول لمحل تجزئة؛ تُقاس مدة الاحتجاز والتنازع ولا يُدّعى أن كلفته صفر.
- **التوسع:** رأسي أولاً؛ الأفقي لاحقاً على طبقة الويب وعمال Celery — Postgres واحد مع نسخ (لا sharding في هذا النطاق).
- **التعافي:** نسخ دورية + PITR على تخزين مستقل؛ الاستعادة تصدر `sync_epoch` جديداً وتتجاهل ردود الجيل القديم وتصالح الأجهزة (§٨.١٢، §١٣.٤). نسخة العميل المحلية المصدَّرة طبقة مستقلة (§١٣.٣).
- **المراقبة (§١٣.٦):** شاشة تشخيص محلية (SYS-11) + لوحة خادمية: تنبيه انقطاع مزامنة 48 ساعة، تراكم حجر، فشل نسخ. صفحة حالة مستقلة عن خادم التطبيق (§١١.٩).

| القرار | البديل المرفوض | الثمن المقبول | المرجع |
|---|---|---|---|
| Modular Monolith | خدمات مصغرة | حدود الوحدات تُفرض بالمراجعة وفحص الاستيراد لا بالشبكة | §٤.١ |
| أحداث ثابتة + تحقق خادمي | CRDT عام | تعارض الأعمال يظهر للمالك بدل حسم تلقائي | §٨.١ |
| قفل عداد المستأجر (ترتيب مضمون للسحب) | تسلسلات مستقلة لكل جدول | سرلسة كتابة المستأجر؛ تُقاس | §٨.٥ |

| النجاح بعد الحفظ المحلي؛ HTTP ليس شرطاً | تأكيد خادمي لكل حفظ | مصالحة لاحقة ولقطات (§٨.٨–٨.٩) | §٤.٦ |
| PWA أولاً ثم Expo ثم Tauri | أصلي أولاً | قيود طباعة Web Bluetooth؛ جهاز لا يطبع لا يُعتمد POS ويب (§١٢.٢) | §١٥.١ |
| بحث PostgreSQL | محرك بحث مستقل | ترقيم صفحات وفهارس مقاسة تكفي النطاق الأول | §٤.٧ |
| Outbox في معاملة العملية | after_commit منفصل للإشعارات فقط؛ لا شيء من صحة البيع خارج المعاملة | جدول إضافي ومستهلك idempotent | §٤.٣ |
| Cookies HttpOnly للتجديد (ويب) | localStorage | تعقيد CSRF/SSR | §٩.٤ |

## ٦ · ما يُعاد النظر فيه مع النمو (§١٩.٢)

1. **تنازع قفل المستأجر** عند مستأجر كثيف الأجهزة — يقاس قبل أي تجزئة للمسار.
2. **نافذة 90 يوماً والتقليم** — توسّع بعد قياس الحجم بالبايت والأداء (§٨.١١).
3. **البحث** — محرك مستقل فقط إن أثبت قياس Postgres قصوراً.
4. **العملات المتعددة** — المفتاح `(party, role, currency)` جاهز؛ الفتح عقد مستقل (§٦.٤).
5. **وحدة التكلفة والهامش** — خلف بوابة G-03؛ `phase_locked` حتى حسم سياسة التكلفة (§٧.٧).
6. **M3 التكامل المالي للسوق** — بعد MK-3 وعقد المشتريات (§١٥.٥).
7. **إعادة ترتيب Tauri/Expo** — خيار مشروط بدليل عملاء وعتاد، لا يتغير تلقائياً (§١٥.١).
8. **حدود الباقات والسعات** — تصميم عرض حتى يمر اختبار تحميل (§١٦.١).
